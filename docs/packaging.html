Context & scope

Repo: ~/claude-code/kdx-hotline · Rust workspace, 7 crates · Server binary: crates/kdxd · Desktop client: apps/kdx-client (Tauri v2, vanilla JS)

All features are shipped and tested (237 tests, 0 TODOs). This session is purely about making both products distributable: clean metadata, a real icon set, bundle config, an example server config, and a tightened README. No new features, no refactoring.

Two products to package:

kdxd daemon

The server binary. Distributed as a compiled executable. SysOps install it on a machine, point it at a TLS cert, run kdxd useradd, start it. Config via kdxd.toml. Traditional port 10700.

KDX desktop app

The Tauri v2 desktop client. Targets macOS first (.app + .dmg), with Windows and Linux as stretch goals. Needs a proper icon set, bundle metadata, and entitlements.

Open questions — decide before starting

Icon source The current icons/icon.png is a placeholder. Does a real icon design exist, or does one need to be created? cargo tauri icon <source.png> generates the full set (32×32 through 512×512, .icns, .ico) from one 1024×1024 source. The source must be provided before the icon step can run.
App Store category Tauri accepts a macOS app category string. Closest fits: public.app-category.social-networking, public.app-category.utilities, or public.app-category.productivity. Pick one — it affects App Store placement if submitted.
Resolved: SocialNetworking (chat app).
macOS minimum version Tauri v2 supports macOS 10.13+. rustls requires 10.13+. Reasonable targets: 10.15 (Catalina, 2019) or 11.0 (Big Sur, 2020). Most users are 12+; 10.15 is the broadest reasonable floor.
Resolved: 10.15.
Target platforms macOS is confirmed (app + dmg). Windows (NSIS installer) and Linux (AppImage, .deb) are possible with Tauri but each needs its own bundle config block and an OS-specific CI runner. In scope for this session or deferred?
Server distribution format Options: (a) GitHub release pre-built binary only, (b) Homebrew tap formula, (c) Docker image, (d) systemd/launchd service files bundled alongside the binary. Minimum is (a); (b) is the most SysOp-friendly for macOS.
Resolved: (a) GitHub release artifacts per OS (zip + service files), built by the CI matrix; (d) service files ship inside each zip.
Copyright holder / year Tauri bundles a copyright string. Suggest: © 2024–2026 theusual. Confirm the name/entity before writing it into config.
Resolved: © 2024–2026 theusual.

2. Example config file done

Create crates/kdxd/kdxd.example.toml

Mirrors every field in src/config.rs with its default value and a comment explaining each. SysOps copy it to kdxd.toml and uncomment what they need. Current fields to document:

# KDX server configuration. Copy to kdxd.toml and pass as the first argument:
#   kdxd kdxd.toml

# Address and port to listen on. Traditional KDX port is 10700.
bind                    = "0.0.0.0:10700"

# SQLite database path. Created automatically on first run.
database                = "kdx.db"

# Directory where uploaded file bytes are stored. Created automatically.
files_root              = "files"

# Session idle timeout in seconds before the server closes the connection.
session_ttl_secs        = 1800

# Per-transfer throttles in bytes/sec. 0 = unlimited.
max_upload_bytes_per_sec   = 0
max_download_bytes_per_sec = 0

# Tracker directory display name and description.
server_name        = "KDX Server"
server_description = ""
max_users          = 256

# TLS certificate and private key (PEM). When omitted, a self-signed
# dev certificate is generated at startup — fine for local testing only.
# [tls]
# cert_pem = "/etc/kdx/cert.pem"
# key_pem  = "/etc/kdx/key.pem"

3. Entitlements plist done

Create apps/kdx-client/src-tauri/entitlements.plist

Enables the macOS App Sandbox. KDX needs outbound TCP connections and the files the user picks — nothing else. See macOS — App Sandbox, signing & notarization.

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>com.apple.security.app-sandbox</key><true/>
  <key>com.apple.security.network.client</key><true/>
  <key>com.apple.security.files.user-selected.read-write</key><true/>
</dict></plist>

files.user-selected.read-write covers the native Open/Save dialogs used by upload and download. A unit test (src/bundle_tests.rs) pins this exact set, so widening it is a deliberate, reviewed change.

macOS — App Sandbox, signing & notarization

1. App Sandbox done needs a macOS check

Entitlements

com.apple.security.app-sandbox — run sandboxed. com.apple.security.network.client — outbound TCP to KDX servers (DNS included). com.apple.security.files.user-selected.read-write — the one file picked in the native Open (upload) or Save (download) dialog.

Deliberately not files.downloads.read-write: the Save dialog merely starts in ~/Downloads (Tauri's download_dir(), which inside the sandbox is the container's Downloads symlink to the real folder); the dialog's own grant covers the file the user picks, wherever it is. Granting the whole Downloads folder would let a compromised webview read and overwrite every file in it. No cs.* hardened-runtime exceptions are needed either: WebKit's JIT runs in Apple's WebContent process, not in KDX.

Where KDX writes

Only inside its container (~/Library/Containers/net.kdx.hotline.client/Data/) or to a dialog-chosen file:

# Tauri app_data_dir (= ClientConfig::data_dir), inside the container:
Library/Application Support/net.kdx.hotline.client/known_hosts.toml      # TOFU pins
Library/Application Support/net.kdx.hotline.client/transfers/<id>.kdxdata # partial download bytes (dir mode 0700)
Library/Application Support/net.kdx.hotline.client/transfers/<id>.kdxpart # its resume sidecar
# WKWebView storage (Address Book bookmarks, settings, window geometry):
Library/WebKit/net.kdx.hotline.client/
# Address Book passwords: login keychain, generic-password items
#   service "net.kdx.hotline.client", account "bookmark:<uuid>"

Downloads used to stage <file>.kdxdata / <file>.kdxpart beside the chosen file and rename into place — impossible under the sandbox, which grants the chosen file but not its siblings. client-core now keeps both in transfers/ (named by a hash of server, remote path and destination, so choosing the same file again resumes, across restarts), hashes the whole partial, and only then moves the verified file to the destination: a rename when it is on the same volume (normally the case for ~/Downloads); otherwise a hash-checked copy via a hidden temp file beside it, or — when the sandbox refuses that temp file — straight into the chosen file. Partials untouched for 7 days are deleted on connect. Downloaded files carry the com.apple.quarantine attribute (the sandbox adds it), so Gatekeeper still vets anything executable a server sent.

Upgrading from an unsandboxed build

A sandboxed app no longer sees ~/Library/Application Support/net.kdx.hotline.client or ~/Library/WebKit/net.kdx.hotline.client. container-migration.plist (bundled as Contents/Resources/container-migration.plist via bundle.macOS.files) makes macOS move both into the container on the first sandboxed launch, keeping pinned server keys (otherwise every server would be a first-contact prompt again), bookmarks and settings. Keychain items need no migration. Downgrading to an unsandboxed build afterwards starts from empty state.

Keychain under the sandbox

The keyring crate's apple-native backend (v3.6) uses the file-based keychain API (SecKeychainCopyDomainDefault + SecKeychainAddGenericPassword/FindGenericPassword) on the user's default (login) keychain. A sandboxed app may create and read its own items there without extra entitlements; the item's access list names the app's code signature. Consequences: with ad-hoc signing every rebuild is a different signature, so macOS asks once ("KDX wants to use … in your keychain" → Always Allow) after each update; a Developer ID build keeps one identity and doesn't ask. If the keychain is unavailable or refuses, saving reports "not saved" and login asks for the password — the app keeps working.

2. Code signing ad-hoc Developer ID wired in CI needs secrets

Entitlements only apply to a signed bundle

tauri.conf.json sets bundle.macOS.signingIdentity to "-", so every cargo tauri build (local and CI) ad-hoc signs KDX.app with --options runtime and entitlements.plist: the sandbox is active even without an Apple Developer account. cargo tauri dev and cargo run -p kdx-client run an unsigned binary — unsandboxed; test sandbox behaviour with a bundled build.

An ad-hoc signed app downloaded from the internet is still blocked by Gatekeeper (not notarized): the user opens it once via System Settings → Privacy & Security → Open Anyway.

Developer ID (for distribution)

APPLE_SIGNING_IDENTITY in the environment overrides the config's "-". .github/workflows/release.yml does this on its own once these repository secrets are set (Settings → Secrets and variables → Actions):

APPLE_CERTIFICATE           # base64 of the "Developer ID Application" .p12  (base64 -i cert.p12 | pbcopy)
APPLE_CERTIFICATE_PASSWORD  # its export password
APPLE_SIGNING_IDENTITY      # "Developer ID Application: Name (TEAMID)"

On the macOS runner the workflow then:

  1. imports the certificate into a throwaway keychain (random password, first in the search list) and checks the identity is in it — deleted again when the job ends, whatever happened;
  2. hands APPLE_SIGNING_IDENTITY (and notarization credentials, below) to cargo tauri build only — no other step sees them, and unset secrets are never exported as empty values;
  3. signs the separately built dmg and the kdxd server binary (hardened runtime, secure timestamp) with the same identity;
  4. verifies every build, ad-hoc or not: codesign --verify --deep --strict, the three sandbox entitlements and container-migration.plist present — a release without the sandbox fails instead of shipping.

Without the secrets (forks, or before they're added) the release is ad-hoc signed exactly as before and the run carries a warning. Half a set of secrets fails the run rather than silently falling back. Consider moving the secrets to a protected environment with required reviewers if more people can push tags.

Locally, with the certificate in your login keychain: APPLE_SIGNING_IDENTITY="Developer ID Application: Name (TEAMID)" cargo tauri build --bundles app.

3. Notarization wired in CI needs an Apple account

Tauri notarizes the .app when credentials are present

Requires a Developer ID signature and the hardened runtime (hardenedRuntime: true, set). Add one complete set of repository secrets — an Apple ID or an App Store Connect API key:

APPLE_ID + APPLE_PASSWORD (app-specific password) + APPLE_TEAM_ID
# or
APPLE_API_ISSUER + APPLE_API_KEY (key id) + APPLE_API_KEY_P8 (the .p8 file's contents)

The workflow writes the .p8 to a private temp file (removed at the end of the job) and passes Tauri APPLE_API_KEY_PATH. Tauri submits KDX.app, waits and staples the ticket; the workflow then notarizes the dmg (built separately with hdiutil, since --bundles app builds only the app) and staples it, and notarizes kdxd-macos.zip (a zip can't hold a stapled ticket, so Gatekeeper checks kdxd online). With credentials, verification also runs stapler validate and spctl --assess on the app and the dmg. Notarization credentials without the Developer ID secrets fail the run. To do it by hand:

xcrun notarytool submit KDX_0.1.0_aarch64.dmg --apple-id "$APPLE_ID" --team-id "$APPLE_TEAM_ID" --password "$APPLE_PASSWORD" --wait
xcrun stapler staple KDX_0.1.0_aarch64.dmg
Verify a build
codesign -d --entitlements - --xml target/release/bundle/macos/KDX.app | plutil -p -   # the three entitlements
codesign -dvv target/release/bundle/macos/KDX.app            # flags=0x10002(adhoc,runtime) or Authority=Developer ID…
codesign --verify --deep --strict --verbose=2 target/release/bundle/macos/KDX.app
ls target/release/bundle/macos/KDX.app/Contents/Resources/container-migration.plist
spctl -a -vv target/release/bundle/macos/KDX.app             # "accepted, source=Notarized Developer ID" (notarized builds only)

While it runs, Activity Monitor (View → Columns → Sandbox) shows Yes for KDX.

4. Manual macOS checklist open

Run on a bundled (signed) build, before tagging a release

1. Fresh install (no ~/Library/Containers/net.kdx.hotline.client): launch; Activity Monitor shows Sandbox = Yes; connect to a server, accept its key; known_hosts.toml appears under ~/Library/Containers/net.kdx.hotline.client/Data/Library/Application Support/net.kdx.hotline.client/.

2. Download to the suggested ~/Downloads location: the Save dialog opens in Downloads; while it runs, nothing appears in Downloads and …/transfers/ holds one .kdxdata + one .kdxpart; afterwards the file is in Downloads, byte-identical (shasum -a 256 against the server copy), transfers/ is empty, and xattr shows com.apple.quarantine.

3. Download over an existing file (confirm "Replace" in the dialog): the old file is replaced.

4. Download to an external / other-volume disk (USB stick, disk image: hdiutil create -size 200m -fs APFS -volname KDXT /tmp/kdxt.dmg && hdiutil attach /tmp/kdxt.dmg): completes, no .*.kdxtmp file left on that volume, transfers/ empty. Repeat with an exFAT volume.

5. Resume: start a large download, Cancel in the Transfers window; quit KDX; relaunch, reconnect, download the same file to the same place (no file exists there yet, so no Replace prompt): progress starts partway and the result is byte-identical. Also with the network dropped mid-download.

6. Upload a file from ~/Documents and from an external volume via the Open dialog: both succeed.

7. Address Book: save a bookmark with a password; quit and relaunch; log in with it without typing the password. Keychain Access shows a generic password "net.kdx.hotline.client" / "bookmark:…" in the login keychain. Delete the bookmark: the item is gone. After installing a rebuilt (ad-hoc) copy, the one-time keychain prompt appears and Always Allow works.

8. Upgrade from an unsandboxed build (e.g. v0.1.0 from the release page, with a pinned server, a bookmark and changed settings): install the sandboxed build over it and launch — the server connects without a first-contact prompt, bookmarks and settings are intact, and ~/Library/Application Support/net.kdx.hotline.client has moved into the container.

9. Console.app, filter "Sandbox" / process KDX, during all of the above: no deny(1) file-write-create or file-read-data violations — except, for a destination on another volume, one refused hidden .<hex>.kdxtmp beside the chosen file (KDX then writes the chosen file in place; the download still succeeds).

10. A stale partial (cancel a download, then set its files' modification time 8 days back with touch -t) is gone after the next connect.
